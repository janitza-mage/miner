
Shader Object: Einzelprogramm
Program Object: Gruppe von mehreren Shaders -> "executable"
Program Pipeline Object: Gruppe von Program Objects; flexibler

Prozess Variante 1:
- load source code into a shader object
- compile
Prozess Variante 2 (geht falls NUM_SHADER_BINARY_FORMATS > 0):
- load SPIR-V code into a shader object
- specialize
Danach:
- attach to program object
- link program object -> erzeugt executable code aus allen Shader Objects an diesem Program Object
Alternativ
load pre-compiled binary code directly into program


shader stage / shader type: Stage der Pipeline zu der der Shader gehört


Current Program Object für eine Stage: PO ist "bound to that stage".
Active Program Object für eine Stage: PO ist current UND enthält einen Shader dieses Typs
Unified PO: Selbes PO für alle stages
Separable PO: unterschiedliche POs für unterschiedliche stages
"The set of separable program objects current for all stages are collected in a program pipeline object that must be bound for use."


Stages:
- vertex
- tessellation control
- tessellation evaluation
- geometry
- fragment
- compute

Variable types:
- uniform: constant during program execution
- buffer: stored in buffer; can be written; persistent across multiple invocations
- subroutine uniform: "similar to uniforms but are context state, rather than program object state"
- samplers: uniforms used for texturing
- images: indentify level of a texture to access
- output

glShaderBinary(shaderCount, shaderArray, binaryformat, binaryPointer, binaryLengthInBytes)
    vordefiniert: binaryformat = SHADER_BINARY_FORMAT_SPIR_V
    setzt den Compile-Status aller Shader auf FALSE
    Bei Fehlschlag ist der State des Shaders trotzdem kaputt
    glLinkProgram kann (impl.specific) fordern, dass alle Shader Binaries eines Programs zusammen compiled+optimized wurden
glSpecializeShader(shader, entryPointUtf8NameNullterminated, numSpecConstants, constantIndexArray, constantValueArray)
    muss vor dem Linken passieren. Ans Program attachen geht aber schon vorher, nur vor dem Linken müssen alle specialized sein.
    man kann nur 1x specializen. Um zu re-specializen, muss zuerst mit glShaderBinary das Binary neu geladen werden
        (d.h. dass die Implementierung das Roh-Binary mit dem Specializen verwerfen darf)
    Wählt Entry-Point; wählt Werte für die Specialization Constants
    Entry Point muss als OpEntryPoint im SPIR-V-Modul deklariert sein
    constantValueArray ist formal ein Array von int32, aber wird in die entsprechenden Typen *bitcasted*
    nicht angegebene SpecConsts behalten ihren Defaultwert
    setzt Compile-Status auf TRUE falls erfolgreich

glLinkProgram(program)
    GetProgramiv mit LINK_STATUS liefert TRUE / FALSE, je nachdem ob errors
    s.95+ sind Gründe, warum das Linken failen kann.
        1+ Shader sind nicht compiled / specialized
        zu viele "active uniform or active sampler variables"
        tesselation control: program ist separable oder vertex shader vorhanden; EINEINDEUTIG(output patch vertex count)
        tesselation evaluation: program ist separable oder vertex shader vorhanden; EINEINDEUTIG(primitive mode); EINDEUTIG(spacing, vertex order, point mode)
        geometry: program ist separable oder vertex shader vorhanden; EINEINDEUTIG(input primitive type, output primitive type, max output vertex count)
        compute shader dürfen nicht mit nicht-compute-shadern gelinked werden
        -- Dabei heißt EINDEUTIG(x): Der Wert x muss nicht definiert sein, aber falls er in
            mehreren Shadern definiert ist, muss er überall den gleichen Wert haben.
        -- Dabei heißt EINEINDEUTIG(x): Der Wert x muss in mind. einem Shader definiert sein, und falls er in
            mehreren Shadern definiert ist, muss er überall den gleichen Wert haben.


"Multiple shader objects of the same type may be attached to a single program object, and a single shader object may be
attached to more than one program object."
-> aber nur ein Shader kann eine main()-Funktion haben. Also ist das wie mehrere Source-Files.

"When program objects which have been linked successfully are used for rendering operations, they may access GL state
and interface with other stages of the GL pipeline through active variables and active interface blocks."
Infos dazu abfragen funktioniert nur nach erfolgreichem Linken zuverlässig, bei Fehlern muss man halt sehen was man
bekommt, aber es kann helfen, den Fehler zu verstehen. Ohne das Linken auch nur zu versuchen kommt leere Info.

glGetProgramInfoLog -> liefert mehr Infos zum Linken

glUseProgram(program) -> Program wird Teil des Rendering State für alle Stages; as hat Vorrang vor einer Program Pipeline.
Das Program heißt "active" für eine Stage, wenn es code für diese Stage enthält

Ohne Vertex Shader / Fragment Shader:
- compat: fixed-function
- core: undefined output, but not an error
Ohne compute: Aufruf ist ein Fehler
Ohne die anderen: jeweils no-op

Alles Rumbasteln an einem Program oder dessen Shaders hat keinen Einfluss auf den Executable Code, solange nicht gelinkt
wird. Erfolgreiches Linken ersetzt das Programm; wenn es aktiv wird, wird es damit sofort wirksam. Es nimmt das Programm
auch raus, wo der neue Code keine Wirkung mehr hat. Erfolgloses linken lässt den alten Code im Rendering State; erst
mit glUse* wird der ersetzt.

glProgramParameteri(program, pname, value) setzt Steuerparameter; werden erst mit glLinkProgram / glProgramBinary wirksam):
- PROGRAM_SEPARABLE (TRUE / FALSE)
- PROGRAM_BINARY_RETRIEVABLE_HINT (TRUE / FALSE): Hint, ob das Binary später abgefragt wird

glDeleteProgram(program): löscht ggf. verzögert falls noch in Verwendung; Shaders werden detached
glIsProgram(program)

glCreateShaderProgramv(type, count, strings) -> ID (s.100)
    Führt alle Schritte für ein separable 1-Shader-Program durch, von source code bis Link. Detached und löscht den
    Shader danach, aber über das Program bleibt er in Verwendung und wird dann später mit dem Programm automatisch
    zusammen gelöscht.
    -> ist aber halt für Source Code, nicht für SPIR-V.
